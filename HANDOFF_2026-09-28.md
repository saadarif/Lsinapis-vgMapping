## Key design decisions (context for later)

- **ngsLD and prune_graph have no bioconda/conda-forge package.** Verified by
  searching bioconda-recipes directly — no recipe for either. They run via
  `container: "docker://ghcr.io/zjnolen/ngsld:1.2.0"` (the same image
  PopGLen, this repo's upstream reference, builds for this exact gap).
  Confirmed by pulling it with `singularity` and inspecting it directly: both
  `ngsLD` (v1.2.0) and `prune_graph` binaries are at `/usr/local/bin/` inside.
- **ngsLD's `--max_kb_dist`** (kb) and **prune_graph's distance filter** (bp)
  are **separate, independent config values** —
  `params.run_ld_estimation.max_kb_dist` vs `.prune_max_dist_bp` — per an
  explicit correction mid-session. `prune_max_dist_bp` only has an effect
  while `<= max_kb_dist * 1000`; a warning is printed at parse time if it
  isn't (see top of `5_LD_estimation.smk`).
- **`prune_beagle.py` is deliberately pandas-free**, streaming the beagle
  line-by-line instead of loading it into a DataFrame (PopGLen's reference
  script uses pandas). This was an explicit choice between two options
  presented to the user — chosen to avoid adding a new conda dependency and
  to stay memory-light on whole-genome beagle files.
- **Beagle column layout** (verified against real data, not assumed):
  `marker, allele1, allele2`, then 3 genotype-likelihood columns per
  individual, in the same order ANGSD was given the BAM list
  (`KEEP_SAMPLES_REL`, from `4_relatedness.smk`). Excluding sample index `i`
  (0-based) means dropping columns `i*3+4, i*3+5, i*3+6` (1-based). This is
  the logic in `pca_exclude_beagle`'s `PCA_EXCLUDE_COLS` — checked directly
  against a real sample (`LsKaz2` → columns 10–12 → confirmed labeled `Ind2`
  in a real beagle header, and `cut --complement` on those columns dropped
  exactly 2 samples' worth of columns from a real file).

## Not done / open risk (nothing is currently known-broken, but flagging)

- **No real, full Snakemake run yet.** Everything above was validated on a
  20 kb / 6,000-site slice, not genome-wide (~2.3M sites total in the real
  relatedness beagle). The DAG resolves cleanly in dry runs; actual runtime
  and memory at full scale are unknown.
- **Performance risk at the current default `max_kb_dist: 5000`** (5 Mb).
  On the 43k-site/20kb-window stress test earlier in the session,
  `prune_graph` alone took **16 minutes** for ~11M edges. Genome-wide, at
  5 Mb windows over 2.3M sites, this could be very slow (hours, unknown
  upper bound — not tested). Options if it turns out to be a problem:
  lower `max_kb_dist`, or chunk by chromosome/scaffold (not currently
  implemented — `5_LD_estimation.smk` runs on the whole beagle file in one
  shot, unlike PopGLen's chunked approach).
- `params.run_pca.exclude_samples` is currently `[]` (empty) in
  `config.yaml` — nobody is actually excluded yet. Before a real PCA (or the
  planned NGSadmix) run, this should be populated from
  `results/relatedness/all.DTOLREF.dedup.sitefilt.bQ20.mq30.dpInd3-30.minInd0.9.maf0.05.pv1e-6.ibsrelate.R0R1KING.tsv`
  (real file, already on disk, 61×60/2 pairs) — look for high R0 / low R1 /
  high KING pairs.

## Background info needed for next week: NGSadmix

Goal stated by user: NGSadmix on "the unlinked and unrelated individuals
beagle file used for pcangsd."

- **That beagle file already exists as a rule output** — it's the *input* to
  `pca_pcangsd`, i.e. the output of `pca_exclude_beagle`:
  ```
  results/structure/pca/all.{ref_name}.{PRUNE_TAG}.{PCA_TAG}.beagle.gz
  ```
  where (from `5_LD_estimation.smk` / `6a_Strucure_angsdPCA.smk`):
  - `PRUNE_TAG = f"{REL_TAG}.maxkb{LD_MAX_KB}.prunebp{LD_PRUNE_MAX_BP}.minr2{LD_MIN_R2}"`
  - `PCA_TAG = "excl-" + "-".join(sorted(exclude_samples)) or "excl-none"`
  - `REL_TAG` comes from `4_relatedness.smk` (bam_stage, site filter, bQ,
    mq, depth, minInd, maf, p-value tags)
  A future NGSadmix rule file should depend on this exact path directly
  rather than re-deriving/duplicating it, so PCA and NGSadmix always run on
  the identical sample set and site set.
- **`KEEP_SAMPLES_REL`** (defined in `4_relatedness.smk`) and
  **`PCA_EXCLUDE_SAMPLES`** (defined in `6a_Strucure_angsdPCA.smk`, already
  filtered to samples actually present in the beagle) are both available as
  plain Python lists once those files are `include:`d — reuse them rather
  than recomputing "who's actually in this beagle file" a third time.
- **NGSadmix is bundled with ANGSD** (not a separate bioconda package) — it
  should already be available in `workflow/envs/angsd.yaml`
  (bioconda `angsd =0.940`), same env as `4_relatedness.smk`'s ANGSD rules.
  This is unconfirmed for next session — verify the binary is actually on
  `PATH` inside that conda env before assuming it "just works" like pcangsd
  did.
- **No container needed for NGSadmix** (unlike ngsLD/prune_graph) — it's a
  normal `conda:` rule.
- **Naming/directory convention to follow:** `results/structure/pca/` was
  created this session; a sibling `results/structure/admixture/` (or
  `ngsadmix/`) would fit the same pattern. Tag file names the same way PCA
  does (reuse `PRUNE_TAG` + `PCA_TAG`, plus whatever's NGSadmix-specific,
  e.g. `k{K}` and a replicate/seed number).
- **Config pattern to follow** (matching `params.run_pca`,
  `params.run_relatedness`, etc. already in `config.yaml`): something like
  `params.run_ngsadmix: {k_values: [...], reps: N, seed: ..., threads: ...,
  extra: ""}`, plus a top-level `run_ngsadmix: TRUE` toggle and a
  `NGSADMIX_TARGETS` list assembled in the new rule file and picked up in
  `Snakefile`'s `get_final_targets` (section 12), matching how sections
  9–11 (relatedness/LD/PCA) were done this session.
- NGSadmix typically needs multiple replicates per K (different random
  seeds) to check convergence (e.g. via CLUMPAK/log-likelihood comparison)
  — worth deciding on a replicate count and a convergence-check step before
  writing the rule, rather than just running once per K.
